# 21 - 2026-11-12: VM load test with benchmark workloads

Sources: `UJEP-LAB/benchmarks/vmload/` (tools in `tools/`, raw data in `results/run_*`); session of 2026-11-12. Follows notes 19 and 20.

## Method

- Template `bench`: 4 vCPU, 1 GiB, Alpine, disk on the Lustre datastore (cache `none`); `bench-wb` is the same with `CACHE="writeback"`.
- `loadtest.py N` creates N VMs (batches of 12), places them with the normal scheduler (all 10 nodes, heads included), starts the benchmark in all of them at one synchronized instant through the qemu guest agent, collects the JSON results (polling until every VM has reported), and terminates the VMs.
- `vmbench` (static C binary, in the guest): CPU = matrix multiply on all vCPUs for 30 s; memory = STREAM triad, 2 threads, 20 s; disk = 128 MB sequential write rate-limited to 20 MB/s with fdatasync every 8 MiB, then 500 random 4 KiB writes each followed by fsync (latency percentiles), then 500 O_DIRECT random 4 KiB reads. Steal ticks are recorded per phase.
- Per node every 5 s: CPU busy/steal, InfiniBand TX/RX, IB error counters, eno1 TX/RX, Lustre client read/write bytes. ATA error lines were counted on every node before and after each step (disk phase kept modest because of the open SATA cable question).

## Findings

1. **CPU and memory scale as expected.** Up to 48 VMs (192 vCPUs on 240 hardware threads) every VM gets the same CPU throughput (21.6 GFLOPS, minimum 20.5). At 72 VMs (288 vCPUs, oversubscribed) the median drops to 18.1 and the slowest VM to 13.3. Memory bandwidth per VM falls steadily (19.8, 17.5, 15.8, 14.6, 11.2 GB/s) as the VMs share the host memory controllers.
2. **The fsync latency is a step, not a slope.** The median is 12 to 19 ms up to 24 VMs and 136 ms at 32 VMs and above, the same value on every node and for 32, 40, 48 and 72 VMs. A node with 3 VMs showed 19 ms in the 24-VM step and 138 ms in the 32-VM step, so it is not a per-node VM count. Something in the write path switches to a fixed per-sync cost once the whole cluster passes a load level between 24 and 32 VMs. Not identified.
3. **Guest cache mode does not move the floor.** With `cache=writeback` the median stays 138 ms; only the tail shrinks (p99 244 against 408 ms, max 308 against 463 ms), as note 19's single-VM result suggested for the median at low load. The 136 ms is below the guest and the qemu cache, in the Lustre/ldiskfs write path.
4. **Observed on an OST (read-only, not conclusive):** the ldiskfs journal there averages 26 ms per commit with a running transaction of about 70 ms, which does not account for 136 ms by itself. `sync_journal` reads 0 on the OSTs (not changed).
5. **No ATA errors** on any node in any step, and no InfiniBand errors. This says nothing yet about the SATA cabling: the disk phase wrote about 128 MB per VM and no drive was driven to saturation.
6. **Throughput is not the limit.** Aggregate Lustre client writes stayed far below what the pool delivers in the sequential tests (1.38 GB/s); the VMs are limited by per-sync latency, not bandwidth.
