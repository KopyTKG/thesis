# 17 - 2026-10-22: HPL (LINPACK) on the cluster

Sources: `UJEP-LAB/benchmarks/hpl` (hpl.csv, raw outputs, README), `UJEP-LAB/opennebula/playbooks/hpl_setup.yml` and `hpl_run.yml`, thesis `data/hpl_data.json` and `data/hpl/`.

## Setup

HPL 2.3 (sha256 `32c5c17d...612830`) built once on Lustre with gcc 11.5 (`-O3 -march=haswell`), Open MPI 4.1.1 over UCX 1.19.1 (RDMA, `rc_verbs`/`ud_verbs` on `mlx5_0`), OpenBLAS 0.3.29 (threaded `libopenblasp`). One MPI rank per socket, 12 BLAS threads per rank, NB 192, matrix size N = sqrt(frac x memory x nodes / 8) with frac 0.75 (0.70 for the 10-node run). The `xhpl` binary and the run directory live on local disk on every node. Everything is Ansible (`just hpl-setup`, `just hpl`, `just hpl-all`).

## Results (all residual checks PASSED)

| Nodes | MPI ranks | N | Grid | Time | GFLOPS | Per node | Scaling vs 1 node | % of nominal Rpeak (2.2 GHz) |
|---|---|---|---|---|---|---|---|---|
| 1 (Compute-1) | 2 | 79,104 | 1 x 2 | 463 s | 713.5 | 713.5 | 100% | 84.5% |
| 5 (Compute-1..5) | 10 | 177,024 | 2 x 5 | 1,064 s | 3,476.5 | 695.3 | 97.5% | 82.3% |
| 10 (8 computes + 2 heads) | 20 | 241,728 | 4 x 5 | 1,395 s | 6,751.0 | 675.1 | 94.6% | 79.9% |

- **6.75 TFLOPS on all 10 nodes**, against a nominal peak of 8.45 TFLOPS (240 cores x 16 DP FLOP/cycle x 2.2 GHz). Predictions made before the runs were 5.2 TFLOPS for 10 nodes (range 4.1-6.1) and about 600 GFLOPS per node; the measured 675-713 GFLOPS per node is above both. Observed clocks were about 2.5-2.6 GHz average over all logical CPUs (idle hyper-threads included), i.e. turbo helped more than assumed.
- **The InfiniBand fabric and MPI over RDMA cost about 5% at 10 nodes** (94.6% scaling); 98-99% of the solve time is the DGEMM update.
- The 10-node run loaded the Lustre servers (heads) too, with `nice` 10 and 70% of memory; Lustre stayed responsive (`lfs df` about 0.014 s throughout, 15-16 GiB of memory free on every node).
- Single runs, NB 192 only, distro OpenBLAS (Intel MKL would probably be 10-20% faster); the 8-computes-only point and an NB sweep were not run. Power draw was not measured; the lab breaker limit (note 12) was the reason for the 1 -> 5 -> 10 node ramp.
- Context for the thesis: this is compute performance; the cluster's design goal is the storage layer for a VM cluster (note 12), so the FLOPS figure is a side result that says the CPUs and the fabric are healthy and well balanced, not the main claim.

## Problems found on the first real runs (all fixed)

1. The Makefile template lacked `HPL_DEFS` (`hpl.h` not found).
2. On Rocky 9 `libopenblas.so` is the **serial** BLAS; the threaded build is `libopenblasp.so`. Linking the former would have made every rank use 1 core instead of 12 without an error.
3. `firewalld` blocked Open MPI's dynamic ports (`ibs1` is in the `public` zone with a port whitelist): fixed with a rich rule accepting only the IB subnet 10.0.0.0/24. A 1-node run never notices.
4. **The `user` account has UID 1001 on Compute-3 and 1000 on every other node** (heads included). Lustre identifies users by UID and the MDS does not know 1001, so `user` on Compute-3 gets "Permission denied" below `/mnt/lustre` (root works). Worked around by staging `xhpl` and the run directory on local disk as root. The mismatch itself is not fixed, and it matters for OpenNebula (the `oneadmin` UID/GID must match on all hosts for a shared datastore).
5. First `mpirun` mapping was `ppr:2:socket` (4 ranks per node) instead of one rank per socket; Open MPI refused it before any load.
